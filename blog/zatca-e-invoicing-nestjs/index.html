ZATCA in NestJS e-invoicing without the panic.

By Bilal Arshad, senior full-stack developer · 13 Oct 2026 · 10 min read

Most ZATCA guides assume you're plugging an off-the-shelf ERP into Fatoora. If you run your own platform — a marketplace, a SaaS, a booking system — you have to build the e-invoicing layer yourself. This is the structure I use on a NestJS + Prisma + PostgreSQL marketplace for Saudi merchants, where every paid order and every refund has to end up as a valid, traceable e-invoice.

1. The two phases, in one paragraph

ZATCA's e-invoicing (Fatoora) rolled out in two phases. Phase 1 (Generation) required invoices to be produced electronically in a compliant format. Phase 2 (Integration) connects your system directly to ZATCA: invoices are produced as UBL 2.1 XML, cryptographically stamped, chained together, and sent to ZATCA's APIs. Phase 2 was rolled out to taxpayers in waves, so check which wave your client is in and the date they were notified for.

2. Clearance vs reporting

The single most important distinction is the invoice type, because it decides the flow:

  • Standard tax invoices (business to business): must be cleared by ZATCA before you share them with the buyer. ZATCA returns the cleared invoice, and that's the version the customer receives.
  • Simplified tax invoices (business to consumer): you issue them immediately with a QR code, then report them to ZATCA within 24 hours.

For a consumer marketplace, almost everything is simplified, which is good news: checkout never has to wait on ZATCA. You issue the invoice, show it to the customer, and report it in the background.

3. Onboarding: CSR, OTP and CSIDs

Each "e-invoicing solution unit" (your system, per taxpayer or branch setup) is onboarded once:

  1. Generate a key pair and a certificate signing request (CSR) with the taxpayer's details.
  2. The taxpayer logs in to the Fatoora portal and generates an OTP.
  3. Your system sends the CSR + OTP and receives a compliance CSID.
  4. You pass ZATCA's compliance checks by submitting sample invoices of each type you'll issue.
  5. You then request the production CSID, which is what you sign real invoices with.

Don't hard-code any of this. On a marketplace the credentials belong to whoever issues the invoice, so I store each connection as a record that admins manage from the dashboard, with the private key encrypted at rest:

// schema.prisma (excerpt)
model ZatcaConnection {
  id              String   @id @default(cuid())
  environment     ZatcaEnv // SANDBOX | SIMULATION | PRODUCTION
  vatNumber       String
  privateKeyEnc   String   // encrypted with a KMS / app key, never plain text
  complianceCsid  String?
  productionCsid  String?
  status          ZatcaConnectionStatus // PENDING_OTP | COMPLIANCE | ACTIVE | DISABLED
  lastInvoiceHash String?
  invoiceCounter  Int      @default(0)
  updatedAt       DateTime @updatedAt
}

Switching from simulation to production is then a data change made by a person with the right role — and it's recorded in the audit log.

4. The invoice chain: counter, UUID and previous hash

Phase 2 invoices form a chain. Each one carries a UUID, an incrementing invoice counter, and the hash of the previous invoice from the same unit. That makes ordering a correctness problem, not a cosmetic one: two invoices created at the same moment must not get the same counter or point at the same previous hash.

The fix is to take the next counter and previous hash inside a transaction that locks the connection row:

// zatca-chain.service.ts
async allocate(connectionId: string) {
  return this.prisma.$transaction(async (tx) => {
    const [conn] = await tx.$queryRaw<{ invoiceCounter: number; lastInvoiceHash: string | null }[]>`
      SELECT "invoiceCounter", "lastInvoiceHash"
      FROM "ZatcaConnection" WHERE id = ${connectionId}
      FOR UPDATE`;

    const counter = conn.invoiceCounter + 1;
    const previousHash = conn.lastInvoiceHash ?? INITIAL_PREVIOUS_HASH;
    const xml = this.builder.build({ counter, previousHash, uuid: randomUUID() /* + invoice data */ });
    const { signedXml, hash, qr } = this.signer.sign(xml, connectionId);

    await tx.zatcaConnection.update({
      where: { id: connectionId },
      data: { invoiceCounter: counter, lastInvoiceHash: hash },
    });
    return { counter, signedXml, hash, qr };
  });
}

INITIAL_PREVIOUS_HASH is the fixed value ZATCA specifies for the first invoice in a chain — take it from their developer documentation rather than from a blog post (including this one). The signed XML and hash are stored with the invoice so they're never regenerated later with different values.

5. A submission pipeline that survives outages

Generation and submission are separate steps. Generation happens synchronously when the order is paid (so the customer gets an invoice and QR code immediately). Submission happens in a queue worker, with retries:

// order paid → invoice issued → queued for ZATCA
await this.prisma.einvoice.create({
  data: { orderId, type: "SIMPLIFIED", counter, xml: signedXml, hash, qr, status: "PENDING" },
});
await this.queue.add("zatca-report", { orderId }, { attempts: 8, backoff: { type: "exponential", delay: 60_000 } });

Every invoice has an explicit status — PENDING, REPORTED, CLEARED, REPORTED_WITH_WARNINGS, REJECTED — and the raw ZATCA response is stored next to it. Warnings are not failures, but they deserve a look; rejections stop the line and alert a human, because the next invoice in the chain depends on this one being right.

Because simplified invoices only need to be reported within 24 hours, a ZATCA outage of a few minutes is a non-event: the queue catches up on its own.

6. Refunds become credit notes

You never edit or delete an issued e-invoice. A refund produces a credit note that references the original invoice, goes through the same chain and the same pipeline, and is reported the same way. On a marketplace I tie this to the payment refund, so one action keeps everything consistent:

  1. The payment gateway confirms the refund amount.
  2. The order and the merchant's wallet are updated in one transaction.
  3. A credit note for that amount is issued against the original invoice and queued for ZATCA.
  4. The customer and merchant are notified, with the bilingual PDF attached.

Partial refunds produce partial credit notes; the sum of credit notes can never exceed the original invoice.

7. Give finance a screen, not a log file

The thing that makes ZATCA calm in production isn't the XML — it's visibility. Finance and support should be able to answer "was this invoice accepted?" without a developer. The admin screen I build shows, per invoice: type, counter, status, ZATCA warnings or errors in plain language, a link to the PDF, and a "resubmit" action that's only enabled for failed submissions. The same screen lets admins manage connections and switch environments, with every change in the audit log.

8. Production checklist

  • Invoice type decided per transaction (standard → clearance, simplified → reporting).
  • CSIDs and private keys stored per connection, encrypted, managed by admins.
  • Counter and previous hash allocated inside a locking transaction.
  • Signed XML, hash and QR stored once and never regenerated.
  • Submission in a queue with retries; status and raw response stored per invoice.
  • Refunds produce credit notes that reference the original invoice.
  • Simulation environment used before production, and switching recorded in the audit log.
  • Bilingual (Arabic/English) PDFs with the QR code for customers.
