Moyasar + NestJS payments you can reconcile.

By Bilal Arshad, senior full-stack developer · 13 Oct 2026 · 9 min read

There's no official NestJS module for Moyasar, and most examples online stop at "show the payment form". In production you also need to verify payments on your server, handle webhooks that arrive more than once, refund safely and reconcile every halala. This guide is the approach I use on a NestJS + Prisma + PostgreSQL marketplace that takes card and STC Pay payments through Moyasar.

1. The architecture: card data never touches your server

Moyasar gives you two kinds of keys. The publishable key (pk_test_… / pk_live_…) can only create payments and is safe to ship in a browser or mobile app. The secret key (sk_…) can do everything and must only live on your backend.

That split decides the flow:

  1. Your NestJS API creates an order and stores the amount it expects, in halalas.
  2. The frontend renders the Moyasar payment form with the publishable key, the same amount, and your order ID in metadata. The customer pays by card, mada, STC Pay or Apple Pay directly with Moyasar.
  3. Moyasar redirects the customer to your callback_url with the payment id.
  4. Your API fetches that payment with the secret key and only marks the order paid if the status, amount, currency and order ID all match.
  5. A webhook confirms the same thing in the background, which covers customers who close the tab before the redirect.

Never trust the query string on the callback by itself. It only tells you which payment to look up.

2. A small Moyasar client in NestJS

Moyasar's API is at https://api.moyasar.com/v1 and uses HTTP Basic auth: the secret key is the username and the password is empty. A thin injectable service is all you need:

// moyasar.service.ts
import { Injectable, Logger } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';

export interface MoyasarPayment {
  id: string;
  status: 'initiated' | 'paid' | 'failed' | 'authorized' | 'captured' | 'refunded' | 'voided' | 'verified';
  amount: number;
  currency: string;
  refunded: number;
  metadata?: Record<string, string>;
  source?: { type: string };
}

@Injectable()
export class MoyasarService {
  private readonly logger = new Logger(MoyasarService.name);
  private readonly baseUrl = 'https://api.moyasar.com/v1';
  private readonly auth: string;

  constructor(config: ConfigService) {
    const key = config.getOrThrow<string>('MOYASAR_SECRET_KEY');
    this.auth = 'Basic ' + Buffer.from(`${key}:`).toString('base64');
  }

  private async request<T>(path: string, init: RequestInit = {}): Promise<T> {
    const res = await fetch(`${this.baseUrl}${path}`, {
      ...init,
      headers: { Authorization: this.auth, 'Content-Type': 'application/json', ...init.headers },
      signal: AbortSignal.timeout(15_000),
    });
    if (!res.ok) {
      const body = await res.text();
      this.logger.error(`Moyasar ${init.method ?? 'GET'} ${path} failed: ${res.status} ${body}`);
      throw new Error(`Moyasar request failed with ${res.status}`);
    }
    return res.json() as Promise<T>;
  }

  getPayment(id: string) {
    return this.request<MoyasarPayment>(`/payments/${encodeURIComponent(id)}`);
  }

  refund(id: string, amount?: number) {
    return this.request<MoyasarPayment>(`/payments/${encodeURIComponent(id)}/refund`, {
      method: 'POST',
      body: JSON.stringify(amount ? { amount } : {}),
    });
  }
}

Keep amounts as integers in the smallest unit (halalas: 100 = 1 SAR) everywhere: in the database, in DTOs and in the form. Floating-point riyals are where reconciliation bugs come from.

3. Verifying a payment after the callback

The callback endpoint looks up the payment and compares it with what you stored, not with anything the client sent:

// payments.service.ts
async confirmPayment(paymentId: string) {
  const payment = await this.moyasar.getPayment(paymentId);
  const orderId = payment.metadata?.order_id;
  if (!orderId) throw new BadRequestException('Payment is not linked to an order');

  const order = await this.prisma.order.findUniqueOrThrow({ where: { id: orderId } });

  const matches =
    payment.status === 'paid' &&
    payment.amount === order.totalHalalas &&
    payment.currency === 'SAR';

  if (!matches) {
    await this.prisma.order.update({ where: { id: order.id }, data: { paymentStatus: 'FAILED' } });
    return { ok: false };
  }

  await this.markOrderPaid(order.id, payment.id);
  return { ok: true };
}

markOrderPaid must be safe to call twice, because the webhook will call it too. Do the update with a condition on the current status, inside a transaction, and record the Moyasar payment ID on a unique column:

async markOrderPaid(orderId: string, paymentId: string) {
  await this.prisma.$transaction(async (tx) => {
    const { count } = await tx.order.updateMany({
      where: { id: orderId, paymentStatus: { not: 'PAID' } },
      data: { paymentStatus: 'PAID', moyasarPaymentId: paymentId, paidAt: new Date() },
    });
    if (count === 0) return;
    // first time only: credit merchant wallets, queue the e-invoice, notify the customer
  });
}

4. Webhooks: fast, verified and idempotent

Each webhook delivery has an event id, a type, a live flag, the payment in data, and the secret_token you set when registering the endpoint in the Moyasar dashboard. Moyasar expects a quick 2xx; if it doesn't get one, it retries five more times over roughly the next few hours. So the controller should check the token, store the event, return immediately and do the work afterwards.

// moyasar-webhook.controller.ts
import { timingSafeEqual } from 'node:crypto';

@Controller('webhooks/moyasar')
export class MoyasarWebhookController {
  constructor(private readonly config: ConfigService, private readonly prisma: PrismaService, private readonly queue: PaymentsQueue) {}

  @Post()
  @HttpCode(200)
  async handle(@Body() event: MoyasarWebhookEvent) {
    const expected = Buffer.from(this.config.getOrThrow<string>('MOYASAR_WEBHOOK_SECRET'));
    const received = Buffer.from(String(event.secret_token ?? ''));
    if (expected.length !== received.length || !timingSafeEqual(expected, received)) {
      throw new UnauthorizedException();
    }

    const created = await this.prisma.webhookEvent.createMany({
      data: [{ id: event.id, type: event.type, payload: event as any }],
      skipDuplicates: true,
    });
    if (created.count === 1) await this.queue.add('moyasar-event', { eventId: event.id });

    return { received: true };
  }
}

The unique id on webhookEvent makes retries harmless: a repeated delivery is stored once and processed once. The worker then routes by type:

switch (event.type) {
  case 'payment_paid':
    // re-fetch with getPayment() and run the same checks as the callback
    return this.payments.confirmPayment(event.data.id);
  case 'payment_failed':
  case 'payment_faild': // spelling used in Moyasar's webhook reference
    return this.payments.markFailed(event.data.id);
  case 'payment_refunded':
    return this.payments.syncRefund(event.data.id);
  case 'payment_voided':
    return this.payments.syncVoid(event.data.id);
}

Re-fetching the payment inside the worker means you act on Moyasar's current state, even if events arrive out of order. Also reject events whose live flag doesn't match the environment, so a test webhook can never mark a production order paid.

5. Refunds that keep orders and wallets in sync

A refund touches several things at once: the payment at Moyasar, the order, the merchant's wallet or pending settlement, the tax invoice (a credit note if you issue ZATCA e-invoices) and the customer notification. Call Moyasar first, then apply everything else in one database transaction based on what Moyasar returned:

async refundOrder(orderId: string, amountHalalas: number, actorId: string) {
  const order = await this.prisma.order.findUniqueOrThrow({ where: { id: orderId } });
  if (amountHalalas <= 0 || amountHalalas > order.totalHalalas - order.refundedHalalas) {
    throw new BadRequestException('Invalid refund amount');
  }

  const payment = await this.moyasar.refund(order.moyasarPaymentId!, amountHalalas);

  await this.prisma.$transaction([
    this.prisma.order.update({
      where: { id: order.id },
      data: { refundedHalalas: payment.refunded, paymentStatus: payment.refunded === payment.amount ? 'REFUNDED' : 'PARTIALLY_REFUNDED' },
    }),
    this.prisma.walletEntry.create({ data: { merchantId: order.merchantId, orderId: order.id, amountHalalas: -amountHalalas, reason: 'REFUND' } }),
    this.prisma.auditLog.create({ data: { actorId, action: 'ORDER_REFUNDED', entityId: order.id, meta: { amountHalalas } } }),
  ]);
}

Using payment.refunded from Moyasar's response as the source of truth means partial refunds can never drift from what was actually returned to the card. For very recent payments, Moyasar also supports voiding instead of refunding, which avoids the refund waiting period for the customer.

6. Reconciliation

Even with callbacks and webhooks, run a daily job that lists the previous day's payments from GET /v1/payments and compares each one with your orders: status, amount, refunded amount and fees. Anything that doesn't match goes to a finance report instead of being "fixed" silently. On a marketplace this is also where settlement statements come from: each merchant's paid orders, minus refunds, minus commission per payment method, equals the payout.

7. Production checklist

  • Secret key only on the server; publishable key only in clients.
  • Amounts stored and compared as integer halalas.
  • Order ID in metadata; never trust callback query parameters alone.
  • Webhook secret_token checked with a constant-time comparison.
  • Webhook events stored by unique ID and processed asynchronously.
  • live flag checked against the environment.
  • "Mark paid" and "refund" are idempotent and run in transactions.
  • Daily reconciliation against Moyasar, with mismatches reported to finance.
